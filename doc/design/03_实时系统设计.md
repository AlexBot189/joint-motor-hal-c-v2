## 1. 概述

外骨骼控制系统对实时性有严格要求：控制指令必须在 1ms 内送达电机，反馈数据必须在 5ms 内到达算法层。本文档记录实时线程模型、优先级设计、延迟预算和测试方法。

---

## 2. 线程模型

### 2.1 线程清单

```
┌─────────────────────────────────────────────────────────────┐
│  线程                    调度策略      优先级   周期        │
├─────────────────────────────────────────────────────────────┤
│  算法线程 (外进程)        SCHED_FIFO   90      任意        │
│─────────────────────────────────────────────────────────────│
│  RT控制线程               SCHED_FIFO   90      1KHz        │
│  CAN接收线程 (HAL内部)    SCHED_FIFO   85      事件驱动     │
│  RT上报线程 (与控...      SCHED_FIFO   80      200Hz       │
│─────────────────────────────────────────────────────────────│
│  状态机线程               SCHED_OTHER  0       50ms 轮询   │
│  SDO遥测线程              SCHED_OTHER  0       0.5ms轮询   │
│  日志drain线程            SCHED_OTHER  0       50ms drain  │
│  ROS轮询 (可选)           SCHED_OTHER  0       按需        │
│  WebServer (可选)         SCHED_OTHER  0       事件驱动     │
└─────────────────────────────────────────────────────────────┘
```

**说明**：当前实现中，控制、上报、安全合并为一个 RT 工作线程 (StarkRtWorker::Run())，在单个线程中顺序执行 ProcessMgmt → ProcessMailbox → PublishFeedback。简化了线程同步，适合当前双电机场景。

### 2.2 RT 工作线程主循环

```cpp
void StarkRtWorker::Run() {
    SetThreadRt();  // SCHED_FIFO + priority + CPU affinity + mlockall

    struct timespec next_wake;
    clock_gettime(CLOCK_MONOTONIC, &next_wake);
    const long period_ns = m_rt.period_us * 1000L;

    while (m_running) {
        // ① 管理命令处理 (enable/disable/estop/recover)
        ProcessMgmt();

        // ② 控制命令消费 (mailbox → PDO)
        ProcessMailbox();

        // ③ 反馈数据上报 (fb_cache → SHM 双Buffer)
        PublishFeedback();

        // ④ 延迟统计样本提交
        m_tracer.commit_sample();

        // ⑤ RT周期号递增
        m_cycle_count++;
        m_shm->rt_cycle = m_cycle_count;

        // ⑥ 精确周期休眠 (absolute sleep, 补偿超限)
        next_wake.tv_nsec += period_ns;
        while (next_wake.tv_nsec >= 1000000000L) {
            next_wake.tv_nsec -= 1000000000L;
            next_wake.tv_sec++;
        }
        int ret = clock_nanosleep(CLOCK_MONOTONIC, TIMER_ABSTIME,
                                  &next_wake, nullptr);
        if (ret != 0) {
            m_overrun_count++;  // 周期超限计数
            clock_gettime(CLOCK_MONOTONIC, &next_wake);
        }
    }
}
```

**关键设计点**：
- 使用 `TIMER_ABSTIME` 而非相对休眠，避免累积误差
- 超限后立即重同步时钟，不追赶丢失的周期
- m_overrun_count 用于监控系统负载

## 3. 优先级设计原则

### 3.1 分层策略

```
优先级 90: 控制线程 (PDO 写入)
    ↑ 最高: 负责电机扭矩/位置/速度指令下发
    │       延迟抖动必须 < 100μs

优先级 85: CAN 接收线程
    ↑ 第二: CAN 帧不可丢
    │       接收后立即缓存，不阻塞

优先级 80: 上报线程
    ↑ 第三: 反馈数据完整性重要，但丢一帧可接受

优先级 0:  非 RT 线程
    │       状态机、SDO遥测、日志、ROS、Web
    ▼       允许阻塞，不干扰 RT 路径
```

### 3.2 为什么合并控制+上报为单线程

- 控制 (1KHz PDO) 和上报 (200Hz SHM) 有数据依赖：需要先处理新命令，再上报新反馈
- 单线程天然保证顺序，无需锁
- 两个操作总耗时远小于 1ms 周期预算，合并没有性能瓶颈
- 简化了线程同步和调试复杂度

### 3.3 CAN 接收线程为什么独立

- CAN 帧到达时间不确定 (驱动板发送抖动)
- 接收线程需要在帧到达时立即取出，否则驱动层 buffer 可能溢出
- HAL 内部实现，不阻塞 RT 工作线程

## 4. RT 线程设置

```cpp
void StarkRtWorker::SetThreadRt() {
    // 1. 设置调度策略和优先级
    struct sched_param sp;
    sp.sched_priority = m_rt.priority;  // 90
    pthread_setschedparam(pthread_self(), SCHED_FIFO, &sp);

    // 2. 锁定内存 (防止 page fault 导致延迟毛刺)
    mlockall(MCL_CURRENT | MCL_FUTURE);

    // 3. 设置 CPU 亲和性
    cpu_set_t cpuset;
    CPU_ZERO(&cpuset);
    CPU_SET(m_rt.cpu_affinity[0], &cpuset);  // CPU3
    pthread_setaffinity_np(pthread_self(), sizeof(cpuset), &cpuset);

    // 4. 设置线程名称 (便于调试和 perf 追踪)
    prctl(PR_SET_NAME, "stark_rt", 0, 0, 0);
}
```

## 5. 延迟预算

### 5.1 控制路径延迟 (算法 → 电机)

```
算法写 mailbox                          T0
    ↓ SHM 写 (~100ns)
RT 检测 mailbox seq 变化                T1 = T0 + ~100ns
    ↓ 解析命令 (~1μs)
PDO 帧组装                              T2 = T1 + ~1μs
    ↓ CAN FD 发送 (~13μs @ 5Mbps 64B)
CAN 帧到达驱动板                        T3 = T2 + ~13μs
    ↓ 驱动板处理 (中断延迟 ~10μs)
电机电流响应                            T4 = T3 + ~10μs
────────────────────────────────────────────────
控制总延迟: ~25μs (不含算法计算时间)
```

### 5.2 反馈路径延迟 (电机 → 算法)

```
电机传感器采样                          T0
    ↓ 驱动板固件处理 (~20μs)
CAN FD 帧发送                           T1 = T0 + ~20μs
    ↓ CAN 传输 (~13μs)
CAN 帧到达 SOC                          T2 = T1 + ~13μs
    ↓ HAL 接收线程 → fb_cache (~5μs)
RT 上报线程读 fb_cache                   T3 = T2 + ~5μs + 周期等待 (最多1ms)
    ↓ 组装 + 写 SHM (~2μs)
算法检测 active_idx 变化                 T4 = T3 + ~2μs
────────────────────────────────────────────────
反馈总延迟: ~1ms (由 1KHz 周期主导)
```

### 5.3 端到端控制环延迟

```
传感器采样 → CAN传输 → SOC处理 → SHM → 算法计算 → mailbox → PDO → 电机响应
     ~1ms       ~15μs     ~5μs    ~100ns   ~900μs    ~100ns   ~15μs    ~10μs
─────────────────────────────────────────────────────────────────────────────
总延迟: ~2ms (2 个控制周期)
```

关键瓶颈：算法计算时间 (~900μs 步态计算)，而非通信层。

## 6. 内存锁定

RT 线程禁止 page fault，因为缺页中断耗时不可预测 (ms 级)：

```bash
# 系统级 RT 配置
# /etc/security/limits.conf
@realtime  -  memlock  unlimited

# 或运行时
ulimit -l unlimited

# 内核参数
# /proc/sys/vm/swappiness = 0   # 尽量不用 swap
```

代码中通过 `mlockall(MCL_CURRENT | MCL_FUTURE)` 锁定所有已分配和未来分配的内存。

## 7. 周期超限检测

RT 工作线程在 `clock_nanosleep` 返回 `EINTR` 或其他错误时，意味着前一周期的工作耗时超过 1ms：

```cpp
if (ret != 0) {
    m_overrun_count++;
    // 不追赶，直接对齐到当前时间开始新周期
    clock_gettime(CLOCK_MONOTONIC, &next_wake);
}
```

`m_overrun_count` 通过 SHM 暴露，`m_shm->cycle_overrun_count` 可由外部监控。

超限原因：
1. CAN 总线突发大量帧
2. 系统中断负载 (网络/USB/磁盘)
3. 其他高优先级 RT 线程占用 CPU

## 8. RT 日志系统

RT 线程不能调用标准日志 (fprintf/syslog 可能触发 malloc 或文件系统操作)。使用无锁 ring buffer：

```cpp
// RT 线程写: lock-free, <1μs
RT_LOG("mailbox overrun: seq=%llu", seq);

// 非 RT drain 线程读: 50ms 间隔
void* log_drain_thread(void*) {
    while (g_log_running) {
        g_rt_log->Drain(rt_log_output_fn);
        usleep(50000);
    }
}
```

ring buffer 溢出时自动覆盖最旧条目，不阻塞 RT 线程。

## 9. 延迟追踪

启用 `STARK_LATENCY_TRACE` 编译选项后，关键路径记录时间戳：

```
反馈路径时间戳:
  ts_can_rx        — CAN 帧到达 HAL
  ts_cache_write   — fb_cache 写入完成
  ts_shm_read      — RT 线程读 fb_cache
  ts_shm_write     — SHM 双 Buffer 切换
  ts_algo_read     — 算法读 SHM (算法填充)
  ts_algo_done     — 算法计算完成 (算法填充)

控制路径时间戳:
  ts_mailbox_read  — RT 线程读到 mailbox 命令
  ts_pdo_sent      — PDO 帧发送完成
```

统计信息通过 SHM 暴露：`fb_total_avg_us/max_us`, `ctrl_total_avg_us/max_us`, `mbox_age_avg_us/max_us`。

### 9.1 mailbox age 追踪

```
mbox_age = RT读到mailbox的时刻 - 算法写入mailbox的时刻
```

如果 mbox_age > 1000μs，说明 SHM 写入到 RT 消费之间有延迟（算法和 RT 不同步，或 CPU 被抢占）。

## 10. 性能监控指标

### 10.1 关键 KPI

| 指标 | 目标 | 测量方法 |
|------|------|----------|
| RT 周期抖动 | < ±50μs | `clock_nanosleep` 超限计数 |
| 控制延迟 | < 100μs | `mbox_age` 统计 |
| 反馈延迟 | < 2ms | `fb_total_avg_us` |
| 周期超限率 | < 0.1% | `cycle_overrun_count / total_cycles` |
| CAN 帧丢帧率 | 0 | HAL 驱动层统计 |
| PDO 发送成功率 | >99.9% | HAL 错误计数 |

### 10.2 监控命令

```bash
# RT 线程状态
cat /proc/$(pidof stark_periph_manager_node)/task/*/status | grep -E "Name|policy|prio"

# CPU 使用
top -H -p $(pidof stark_periph_manager_node)

# 延迟追踪 (通过 Web 调试面板)

# 周期超限
grep "overrun" /var/log/stark_node.log

# ftrace 分析延迟毛刺
trace-cmd record -e sched_switch -p function_graph stark_rt
```

## 11. CPU 隔离建议

生产环境建议将 RT 核心隔离，避免非 RT 任务抢占：

```bash
# 内核启动参数
isolcpus=3 rcu_nocbs=3 nohz_full=3

# 或通过 cgroup
mkdir /sys/fs/cgroup/cpuset/rt
echo 3 > /sys/fs/cgroup/cpuset/rt/cpus
echo 0 > /sys/fs/cgroup/cpuset/rt/mems
echo $PID > /sys/fs/cgroup/cpuset/rt/tasks
```

当前配置使用 CPU3 作为 RT 核心 (`cpu_affinity: [3]`)。

## 12. 调试与问题排查

### 12.1 RT 优先级被降级

`SCHED_FIFO` 优先级可能被 `RT_RUNTIME_GREED` 预算限制：

```bash
# 检查
cat /proc/sys/kernel/sched_rt_runtime_us  # 默认 950000 (95%)

# 如果预算不足，RT线程会被限流
# 临时解决:
echo -1 > /proc/sys/kernel/sched_rt_runtime_us
```

### 12.2 内核抢占延迟

`CONFIG_PREEMPT_RT` 内核可显著降低中断延迟。检查：

```bash
uname -a | grep PREEMPT_RT
```

非 RT 内核最大延迟可能达到数百 μs，RT 内核通常 < 20μs。

### 12.3 IRQ 干扰

CAN 控制器的 IRQ 如果和其他高负载外设共享，可能导致延迟抖动：

```bash
cat /proc/interrupts | grep can
# 检查是否可以设置 IRQ affinity
echo 3 > /proc/irq/<irq_num>/smp_affinity
```
