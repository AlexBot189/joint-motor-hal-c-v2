## 1. 概述

外骨骼控制系统对实时性有严格要求：控制指令必须在 1ms 内送达电机，反馈数据必须在 5ms 内到达算法层。

本文档记录：全系统核心分配、线程模型、优先级设计、延迟预算、配置方法、调试手段。

**硬件平台**: RV1126B (4×Cortex-A35)  
**内核**: Linux 6.1.141-rt36 (PREEMPT_RT)  
**CAN**: rk3576_canfd, 1Mbps arbitration + 5Mbps data (CAN FD BRS)

## 2. 全系统核心分配

### 2.1 4 核分配方案

```
┌─────────────────────────────────────────────────────────────────┐
│ Core 3  RT 独占 (isolcpus=3)    │ Core 2  算法                  │
│                                 │                               │
│ stark_periph_manager_node:      │ 助力控制算法  SCHED_FIFO 85    │
│  RT Worker      SCHED_FIFO 90   │ 步态分析      SCHED_FIFO 60    │
│  CAN Recv       SCHED_FIFO 85   │ 状态分析      SCHED_FIFO 40    │
│  SYNC Timer     SCHED_FIFO 80   │                               │
│  IMU HAL        SCHED_FIFO 55   │                               │
├─────────────────────────────────┼───────────────────────────────┤
│ Core 0  系统 + 全部 IRQ         │ Core 1  应用层                │
│                                 │                               │
│ CAN IRQ, GPIO IRQ, WiFi IRQ     │ 主线程 main_loop  SCHED_OTHER │
│ WiFi kthread    SCHED_FIFO 50   │ GPIO Monitor      SCHED_OTHER │
│ 内核线程 (RCU/workqueue/...)    │ IoT 通信          SCHED_OTHER │
│                                 │ 语音处理          SCHED_FIFO 45│
│                                 │ 日志 / Web        SCHED_OTHER │
└─────────────────────────────────┴───────────────────────────────┘
```

### 2.2 隔离策略

```bash
# 内核 cmdline (U-Boot bootargs 追加):
isolcpus=3 rcu_nocbs=3 nohz_full=3 irqaffinity=0-2
```

| 参数 | 作用 |
|------|------|
| `isolcpus=3` | 内核调度器禁止将普通任务放到 Core 3 |
| `rcu_nocbs=3` | RCU 回调不在 Core 3 执行 |
| `nohz_full=3` | Core 3 关闭定时器 tick（单任务运行时） |
| `irqaffinity=0-2` | 所有硬中断只在 Core 0-2 处理 |

**效果**: Core 3 上只能通过 `pthread_setaffinity_np` 或 `taskset` 显式绑定的线程才能运行。代码中 RT Worker、CAN Recv、SYNC、IMU 均已主动绑核。

### 2.3 算法进程隔离

```bash
# cgroup cpuset 限制算法进程到 Core 2
mkdir -p /sys/fs/cgroup/cpuset/algo
echo 2 > /sys/fs/cgroup/cpuset/algo/cpus
echo 0 > /sys/fs/cgroup/cpuset/algo/mems
echo $(pidof algo_sim) > /sys/fs/cgroup/cpuset/algo/tasks
```

### 2.4 WiFi 线程限制

```bash
# 确保 WiFi kthread 不上 Core 3
for p in $(pgrep -f "wifi_frw\|wifi_rx\|usb_wifi"); do
    taskset -pc 0-2 $p
done
```

## 3. 线程模型

### 3.1 线程清单

```
┌──────────────────────────────────────────────────────────────┐
│ 线程                      调度策略      优先级    周期        │
├──────────────────────────────────────────────────────────────┤
│ stark RT Worker            SCHED_FIFO   90        1KHz       │
│ CAN 接收线程               SCHED_FIFO   85        事件驱动    │
│ SYNC 定时器线程            SCHED_FIFO   80        1KHz       │
│ IMU HAL 后台线程           SCHED_FIFO   55        事件驱动    │
├──────────────────────────────────────────────────────────────┤
│ 主线程 (main_loop)         SCHED_OTHER  19        50ms 轮询  │
│ SDO 遥测线程               SCHED_OTHER  19        5ms 轮询   │
│ GPIO 监听线程 (按键)        SCHED_OTHER  19        事件驱动    │
│ 日志 drain 线程             SCHED_OTHER  19        50ms drain │
│ WebServer (可选)           SCHED_OTHER  19        事件驱动    │
├──────────────────────────────────────────────────────────────┤
│ 外部进程:                                                   │
│ 助力控制算法               SCHED_FIFO   85        1KHz       │
│ 步态分析                   SCHED_FIFO   60        100-200Hz  │
│ 状态分析                   SCHED_FIFO   40        10Hz       │
│ 语音处理                   SCHED_FIFO   45        事件驱动    │
│ IoT 通信                   SCHED_OTHER  19        事件驱动    │
└──────────────────────────────────────────────────────────────┘
```

### 3.2 优先级层级

```
FF 90  RT Worker          ← 1KHz PDO 控制 (最关键, 不可超时)
FF 85  助力控制算法        ← 1KHz 力/位置闭环
FF 85  CAN Recv           ← CAN 帧接收+分发 (不可丢帧)
FF 80  SYNC Timer         ← CANopen SYNC 帧
─────────────────── 硬实时分界线 ───────────────────
FF 60  步态分析            ← 相位检测/模式识别
FF 55  IMU HAL            ← IMU 传感器 (高于 WiFi 50)
FF 50  WiFi kthread       ← 固件消息处理
FF 45  语音处理            ← 关键词/TTS
FF 40  状态分析            ← 安全检测/异常
─────────────────── 软实时分界线 ───────────────────
TS 19  主线程/IoT/Log/Web  ← 延迟可容忍
```

### 3.3 优先级可配置

所有 stark RT 线程优先级通过 `config.json` 配置，缺省使用默认值：

```json
"rt": {
    "enable_rt": true,
    "control_priority": 90,
    "recv_priority":    85,
    "sync_priority":    80,
    "imu_priority":     55,
    "control_period_us": 1000,
    "sync_period_us":   1000,
    "report_divider":   1,
    "cpu_affinity": [3]
}
```

| 字段 | 对应线程 | 默认值 | 范围 |
|------|---------|--------|------|
| `control_priority` | RT Worker | 90 | 1-99 |
| `recv_priority` | CAN 接收 | 85 | 1-99 |
| `sync_priority` | SYNC 定时器 | 80 | 1-99 |
| `imu_priority` | IMU HAL | 55 | 1-99 |
| `control_period_us` | RT Worker 周期 | 1000µs | ≥500µs |
| `sync_period_us` | SYNC 帧周期 | 1000µs | ≥500µs |
| `cpu_affinity` | 所有 RT 线程绑核 | [3] | CPU 编号数组 |
| `report_divider` | 上报分频 | 1 | 1-100 |
| `enable_rt` | 启用 SCHED_FIFO | true | true/false |

**实现**: 配置在 `motor_init.cpp` 解析，setter 在对应线程 start 前调用。旧 config 缺少新字段时，`json.value(key, default)` 自动回退默认值，向下兼容。

### 3.4 为什么控制+上报合并为单线程

- 控制 (1KHz PDO) 和上报 (SHM) 有数据依赖：需要先处理新命令再上报新反馈
- 单线程天然保证顺序，无需锁
- 两个操作总耗时远小于 1ms 周期预算
- 简化线程同步和调试复杂度

### 3.5 CAN 接收线程为什么独立

- CAN 帧到达时间不确定（驱动板发送抖动）
- 接收线程需要在帧到达时立即取出，否则驱动层 buffer 可能溢出
- HAL 内部实现，不阻塞 RT 工作线程

## 4. RT 线程设置

```cpp
void StarkRtWorker::SetThreadRt() {
    // 1. 调度策略和优先级 (config.json 可配)
    struct sched_param sp;
    sp.sched_priority = m_rt.priority;
    pthread_setschedparam(pthread_self(), SCHED_FIFO, &sp);

    // 2. 锁定内存 (防止 page fault 导致延迟毛刺)
    mlockall(MCL_CURRENT | MCL_FUTURE);

    // 3. CPU 亲和性 (config.json cpu_affinity)
    cpu_set_t cpuset;
    CPU_ZERO(&cpuset);
    CPU_SET(m_rt.cpu_affinity[0], &cpuset);
    if (m_rt.cpu_affinity[1] >= 0) CPU_SET(m_rt.cpu_affinity[1], &cpuset);
    pthread_setaffinity_np(pthread_self(), sizeof(cpuset), &cpuset);

    // 4. 线程名称 (调试/追踪用)
    prctl(PR_SET_NAME, "stark_rt", 0, 0, 0);
}
```

## 5. 延迟预算

### 5.1 控制路径 (算法 → 电机)

```
算法写 mailbox                          T0
    ↓ SHM 写 (~100ns)
RT 检测 mailbox seq 变化                T1 = T0 + ~100ns
    ↓ 解析命令 (~1μs)
PDO 帧组装                              T2 = T1 + ~1μs
    ↓ CAN FD 发送 (~13μs @ 5Mbps 64B)
CAN 帧到达驱动板                        T3 = T2 + ~13μs
    ↓ 驱动板处理 (~10μs)
电机电流响应                            T4 = T3 + ~10μs
────────────────────────────────────────────────
控制总延迟: ~25μs (不含算法计算时间)
```

### 5.2 反馈路径 (电机 → 算法)

```
电机传感器采样                          T0
    ↓ 驱动板固件处理 (~20μs)
CAN FD 帧发送                           T1 = T0 + ~20μs
    ↓ CAN 传输 (~13μs)
CAN 帧到达 SOC                          T2 = T1 + ~13μs
    ↓ HAL 接收线程 → fb_cache (~5μs)
RT 线程读 fb_cache                       T3 = T2 + ~5μs + 周期等待 (最多1ms)
    ↓ 组装 + 写 SHM (~2μs)
算法检测 active_idx 变化                 T4 = T3 + ~2μs
────────────────────────────────────────────────
反馈总延迟: ~1ms (由 1KHz 周期主导)
```

### 5.3 CAN 到达延时

CAN 帧时间戳 → RT Worker 读到 fb_cache 的时间差，是衡量实时性的关键指标：

| 指标 | 正常 | 异常 (WiFi 抢占 Core 3) |
|------|------|------------------------|
| 平均 | <500µs | 386µs |
| 最大 | <1000µs | 6962µs (6.96ms!) |

**尖峰根因**: WiFi 固件消息线程 (`wifi_frw_msg` SCHED_FIFO 50) 被硬编码绑在 Core 3，处理认证/扫描时占用 2-5ms，阻塞 CAN Recv 线程。

**解决**: WiFi 驱动 patch 移除 Core 3 绑定；`isolcpus=3` 禁止非 RT 任务上 Core 3。

### 5.4 端到端控制环

```
传感器采样 → CAN传输 → SOC处理 → SHM → 算法 → mailbox → PDO → 电机响应
    ~1ms      ~15μs     ~5μs    ~100ns  ~900μs   ~100ns   ~15μs  ~10μs
───────────────────────────────────────────────────────────────────────
总延迟: ~2ms (2 个控制周期)
```

关键瓶颈：算法计算时间 (~900µs 步态计算)，而非通信层。

## 6. 内存锁定

RT 线程禁止 page fault，缺页中断耗时不可预测 (ms 级)：

```bash
# /etc/security/limits.conf
@realtime  -  memlock  unlimited
```

代码通过 `mlockall(MCL_CURRENT | MCL_FUTURE)` 锁定所有内存页。

## 7. 周期超限检测

```cpp
if (ret != 0) {
    m_overrun_count++;  // SHM 暴露: m_shm->cycle_overrun_count
    clock_gettime(CLOCK_MONOTONIC, &next_wake);  // 不追赶, 对齐当前时间
}
```

超限原因：
1. CAN 总线突发大量帧
2. 非 RT 任务抢占 RT 核心 (未配置 isolcpus 时)
3. WiFi 固件消息长时间占用 Core 3
4. 周期内工作耗时超过 1ms

## 8. RT 日志系统

RT 线程不能调用标准日志 (fprintf/syslog 可能触发 malloc 或文件系统操作)。使用无锁 ring buffer：

```cpp
// RT 线程写: lock-free, <1μs
RT_LOG("mailbox overrun: seq=%llu", seq);

// 非 RT drain 线程读: 50ms 间隔
void* log_drain_thread(void*) {
    while (g_log_running) {
        g_rt_log->Drain(rt_log_output_fn);
        usleep(50000);
    }
}
```

## 9. 延迟追踪

启用 `STARK_LATENCY_TRACE` 后，关键路径记录时间戳：

```
反馈路径:  T1 fb_read_start → T2 fb_read_done → T3 mock_sensor_done → T4 shm_write_done
控制路径:  T5 mailbox_read → T6 pdo_sent
```

统计通过 SHM 暴露：`fb_proc_avg_us/max_us`, `ctrl_cmd_avg_us/max_us`, `can_delay_avg_us/max_us`。

### 9.1 延时字段说明

| 字段 | 含义 | 正常值 |
|------|------|--------|
| `can_delay_avg_us` | CAN 帧到达 → RT 读到的平均延时 | <500µs |
| `can_delay_max_us` | 最大 CAN 到达延时 | <1000µs |
| `fb_proc_avg_us` | 反馈处理平均时间 | 2-7µs |
| `fb_proc_max_us` | 反馈处理最大时间 | <20µs |
| `ctrl_cmd_avg_us` | 控制命令处理平均时间 | <5µs |

## 10. 性能监控

### 10.1 关键 KPI

| 指标 | 目标 | 测量方法 |
|------|------|----------|
| RT 周期抖动 | < ±50µs | `cycle_overrun_count` |
| CAN 到达延时 | < 1000µs | `can_delay_max_us` |
| 反馈处理延时 | < 20µs | `fb_proc_max_us` |
| 周期超限率 | < 0.1% | `overrun_count / total_cycles` |
| CAN 帧丢帧率 | 0 | HAL 驱动层 rx_err |

### 10.2 监控命令

```bash
# 全系统线程一览
ps -eLo pid,tid,psr,cls,pri,comm | grep -E "stark_periph|wifi_frw|wifi_rx|usb_wifi|irq/.*can"

# RT 线程详细信息
PID=$(pidof stark_periph_manager_node)
for tid in $(ls /proc/$PID/task/ | sort -n); do
    name=$(grep "^Name:" /proc/$PID/task/$tid/status | awk '{print $2}')
    policy=$(chrt -p $tid 2>/dev/null | grep "policy:" | sed 's/.*: //')
    prio=$(chrt -p $tid 2>/dev/null | grep "priority:" | awk '{print $NF}')
    cpus=$(grep "Cpus_allowed_list:" /proc/$PID/task/$tid/status | awk '{print $2}')
    printf "tid=%-6s name=%-18s %-12s prio=%-4s cpus=%s\n" "$tid" "$name" "$policy" "$prio" "$cpus"
done

# 周期超限
grep "overrun" /var/log/stark_node.log

# 延迟追踪 (Web 接口)
curl http://device:8080/api/latency 2>/dev/null

# CAN 中断
cat /proc/interrupts | grep can
```

## 11. 校准流程时序

校准在状态机线程（非 RT, SCHED_OTHER, 50ms 轮询）中执行，不占用 RT 时间片。

```
T=0        Step 1: Shutdown (0x6040=0x06)     SDO
T=50       Step 2: 机械零位 (0x2531 sub=0)     SDO
T=70       Step 2.5: 力矩零漂 (0x2531 sub=2)   SDO  ← 失败不中断
T=70+      Step 3: 使能 (0x06→0x07→0x0F)       SDO ×3
T=190      Step 4: 设模式 (0x6060)             SDO
T=190+     Step 5: 开透传 (0x5503:04)          SDO
────────────────────────────────────────
总耗时: ~200ms  超时: 10s
```

## 13. WiFi PREEMPT_RT 兼容性

WS73 (Lierda UB37/DB37) 驱动 v1.10.113 在 PREEMPT_RT 内核上有两个兼容问题：

1. `hmac_vap.c` — `local_bh_disable/enable` 与 `preempt_disable/enable` 嵌套在 RT 上语义不一致
2. `frw_thread.c` — WiFi kthread 硬编码绑 Core 3，抢占 RT 线程

修复 patch: `tools/ws73_preempt_rt_fix.patch`  
详细记录: `doc/debug/RT系统调试手册.md`
